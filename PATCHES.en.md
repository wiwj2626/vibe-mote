## 0. Summary

Upstream could not drive **this particular remote** for two independent reasons. Each is fixed
here, plus "hold to repeat", two new action types, and a **single / double / long-press** gesture
layer (timing lifted from the RC003 reference implementation).

| Problem | Symptom | Root cause | Fix |
| --- | --- | --- | --- |
| No key responds | Hook attaches, UI says "running", nothing happens | **Usage table does not overlap at all** (§1) | Per-report-ID tables; added the `0x0003–0x000F` table |
| Same | Self-check: `"remote read" calls: 0` | **The frida bypass never fires on this driver** (§2) | New `hidlocal.py`: read HID collections directly |
| Holding a D-pad key moves one step | One step, then nothing | Windows auto-repeat is generated by the **keyboard driver**; `SendInput` keydowns do not trigger it | New `repeat` flag, software auto-repeat (§3) |
| Want "type fixed text and hit send" | Text only, no Enter | Upstream `text` type sends text only | `text` accepts `enter: true` (§4) |
| Want "press a key to open a URL" | Keys/mouse only | No such action type | New `open` type (§4) |
| Want one key to do different things | One mapping per key | Upstream only knows "down" and "up" | **Gesture layer**: `double` / `long` sub-mappings (§5) |
| Text needs a second OK press to send | Text stops in the input box | Upstream UI has no "auto Enter" switch | UI switch "Press Enter after typing", auto-checked for text (§5.4) |
| Voice key does nothing, then even the D-pad dies | Log: `缺少 ATVV 特征（枚举到 5 个服务）`, then endless retries | **Startup order inverted**: voice grabs the single BLE link first and its retries also starve the HID stack (§8) | Start HID first and wait for it to hold the link; voice only connects inside a "a key was just pressed" window (§8) |
| Voice key pressed but no audio, no text | Log: `本段 0~5 帧音频` | `GET_CAPS` is sent only once at connect time; the remote never re-enters recording state after sleeping | Re-send `GET_CAPS` twice on the next press when the previous press was starved (§8.5) |
| Keys dead after a battery swap / re-pair | Log: `重新打开失败，退回 frida 旁路` | It hands over to frida as soon as HID cannot be opened, and frida reads nothing here | Retry every 2 s; once local reading worked it never falls back to frida (§8.6) |
| Bluetooth shows "connect then immediately disconnect" | Voice connects every 3 s, right into the HID rebuild | Voice misreads "HID not open yet" as "HID absent" | Three-state guard: hands off entirely while `reconnecting` (§8.6) |

## 1. Usage tables do not overlap

Upstream's `USAGE_TO_KEY` assumes **report ID `0x02` + usage `0x0042` = Up**.
Google "A3 / CR PVT / firmware 26.5" emits something entirely different:

| Key | Raw report | Report ID | Usage |
| --- | --- | --- | --- |
| Up | `01 03 00` | 0x01 | 0x0003 |
| Down | `01 04 00` | 0x01 | 0x0004 |
| Left | `01 05 00` | 0x01 | 0x0005 |
| Right | `01 06 00` | 0x01 | 0x0006 |
| OK | `01 07 00` | 0x01 | 0x0007 |
| Home | `01 0A 00` | 0x01 | 0x000A |
| Back | `01 0B 00` | 0x01 | 0x000B |
| YouTube | `01 0E 00` | 0x01 | 0x000E |
| Netflix | `01 0F 00` | 0x01 | 0x000F |

**Not a single usage overlaps**, so no key can ever match — the log says "ready" and nothing happens.

### Fix

```python
USAGE_TO_KEY_RC01 = {
    0x0003: "up", 0x0004: "down", 0x0005: "left", 0x0006: "right",
    0x0007: "ok", 0x000A: "home", 0x000B: "back",
    0x000E: "youtube", 0x000F: "netflix",
}
REPORT_TABLES = {0x01: USAGE_TO_KEY_RC01, 0x02: USAGE_TO_KEY}

def usage_table_for(report_id):
    return REPORT_TABLES.get(report_id, USAGE_TO_KEY)
```

Three consistent follow-ups:

- `_on_report` / `_release`: pick the table **by report ID**; `_held` now stores
  `(report_id, usage)` instead of `usage` — otherwise the two tables cross-contaminate.
- `_push_block`: collect blockable usages **across all tables**. It used to derive them from
  `KEY_TO_USAGE` (reverse of the standard table only), so every `0x03–0x0F` was missed —
  while the UI still proudly reported "blocked N keys".
- `selfcheck()`: look up observed usages in `USAGE_TO_KEY_RC01` too, or the diagnostic
  prints "unknown" for every key.

### Adding another remote model

1. Run **Settings → Diagnostics → key-mapping self-check**, read the `seen` line;
2. add a `USAGE_TO_KEY_<n>` table for those usages;
3. register it in `REPORT_TABLES`.

> ⚠️ Do **not** append to `USAGE_TO_KEY` directly — that table belongs to report ID `0x02`,
> mixing them makes other BLE keyboards/mice match by accident.

## 2. The frida bypass is empty on this machine

Upstream hooks `ntdll!NtDeviceIoControlFile` inside `WUDFHost.exe` and copies the output buffer
of IOCTL `0x80018483`. On a real machine the self-check says:

```
Key-mapping self-check: attached to host PID 5356 (2 WUDFHost processes on this machine),
0 “remote read” calls in that host, output lengths: none; 0 key reports received.
Injection test: attaching to an ordinary process succeeded → frida itself is fine
```

**frida attaches fine, but that IOCTL is never called** — this Bluetooth HID driver simply does
not read reports that way, so the whole bypass is dead air. Meanwhile a plain `ReadFile` on the
Consumer collection delivers `01 03 00` reliably.

### Fix: new `hidlocal.py`

Enumerates `\\?\HID#...` interfaces with `SetupDiGetClassDevs` / `SetupDiEnumDeviceInterfaces`,
filters by **VID/PID + usage page 0x0C**, then blocks on `ReadFile`.

`keys.py` tries it first:

```python
def run(self):
    if self._run_local_hid():     # ★ if this works, frida is never touched
        return
    try:
        import frida
    ...
```

### Three pitfalls, all hit for real

**① `SetupDiGetClassDevsW.restype` must be declared**

```python
setupapi.SetupDiGetClassDevsW.restype = ctypes.c_void_p   # without this: always 0 devices
```

On 64-bit Windows an undeclared `restype` truncates the returned HANDLE to `int32`;
`SetupDiEnumDeviceInterfaces` then gets a garbage handle, **enumeration returns an empty list and
raises nothing**. Looks like perfectly correct code that mysteriously finds nothing.

**② `ReadFile` failure must be reported upward, never retried in place**

```python
def read_loop(handle, on_report, stop_event, buffer_len=64):
    ...
    if not ok:
        return False        # let the caller re-enumerate and reopen
```

Swallowing the error in an inner `while True` means: after the device is re-enumerated (re-pair,
Bluetooth disconnect, driver reload) the **process is still alive, the UI still says "running",
and not a single report arrives**. A sibling project lost hours to exactly this.

The caller clears `_held`, re-enumerates, reopens, and backs off exponentially (1s → 10s).

**③ Mutually exclusive with frida, but interoperable**

When local HID works, `tap.js` is never loaded; otherwise it falls back to frida automatically.
Both paths feed the same `_on_report`, so behaviour is identical.

### Trade-off

| | |
| --- | --- |
| ✅ | No admin rights, no injection into system processes, no `frida-*` temp services, no UAC prompts |
| ⚠️ | No "nullify" capability (zeroing the usage to suppress native actions). `0x03–0x0F` have no native action on Windows, so there is no double-fire |

## 3. Auto-repeat (`repeat`)

### Why `hold` cannot repeat

`hold` sends a keydown and simply keeps the key down. On a physical keyboard that repeats because
**auto-repeat is generated by the keyboard driver** — the key stays down and the driver emits a
keydown every ~30 ms.

`SendInput`-injected keys never pass through the keyboard driver, so Windows generates no repeat.
Result: one step per press, nothing while holding.

> Upstream clearly ran into this: its default maps Up/Down to `holdmouse` + wheel repeat rather
> than arrow keys.

### Fix

```python
REPEAT_INITIAL_K  = 0.35    # delay before repeating (a tap stays a single step)
REPEAT_INTERVAL_K = 0.08    # ~12 repeats per second
```

```json
"up": {"type": "hold", "value": "UP", "mods": [], "text": "", "repeat": true}
```

Uses tap (down+up) rather than repeated keydowns, because some editors only accept complete
press/release pairs. `up()` stops the repeater first; `release_all()` does too.

## 5. Gestures: single click / double click / long press

### 5.1 Config shape

A key keeps its existing mapping (= **single click**) and may carry two optional sub-mappings:

```json
"ok": {
  "type": "key", "value": "ENTER",
  "double": {"type": "key",  "value": "ESC"},
  "long":   {"type": "text", "text": "/clear", "enter": true}
}
```

- **The top-level entry is unchanged**, so old configs keep working byte for byte.
- `double` / `long` are **complete mappings** with the same fields as the top level — so
  "long press opens a URL" or "double click types a sentence" both work out of the box.
- Only one level deep. A `double` nested inside a `double` is dropped when saving.

### 5.2 Timing

These numbers are not guesses — they are copied from the
**[RC003 / windows-remote-mic-app](https://github.com/ZSTDJan/windows-remote-mic-app)**
`button_gesture.py`, where they were tuned against real hardware:

| Constant | Value | Meaning |
| --- | --- | --- |
| `GESTURE_DOUBLE_S` | **0.30 s** | Max gap between the two presses; longer = two single clicks |
| `GESTURE_LONG_S` | **0.55 s** | Hold longer than this and it is a long press |

| Configured | Short press | Hold ≥0.55 s | Two presses, gap <0.30 s |
| --- | --- | --- | --- |
| Single only | **Fires on press** (zero latency, exactly like upstream) | — | Fires twice |
| Single + long | Fires on release | Long press, **swallows** the single | Two singles |
| Single + double | **Delayed 0.30 s** (waiting for the second press) | — | Double |
| All three | Delayed 0.30 s | Long press, swallows single | Double |

> **Configuring a double click always delays the single click by 0.30 s.** That pause exists
> to see whether a second press is coming; every phone does the same. **Do not put a double
> click on the D-pad** if you want it to feel immediate.

> **A double/long press disables `repeat`** — the press duration is now used to detect a long
> press, so auto-repeat cannot coexist. `_fire()` strips `repeat` explicitly (otherwise the
> single click would start repeating forever after release).

### 5.3 Implementation: one layer between KeyTap and Player

```
HID report → KeyTap._on_report → GestureRouter.press/release → Player.down/up → SendInput
                                       ↑
                              threading.Timer ×2 (long press / double-click window)
```

`GestureRouter` (in `keys.py`) is a pure state machine with one state dict per key:

```python
st = {"pressed", "second", "waiting_double", "long_fired",
      "immediate", "long_timer", "long_token", "double_timer", "double_token",
      "single", "double", "long", "held_sub"}
```

Details that **have** to be written this way (all learned the hard way):

1. **Timers carry a token.** A release and a "long-press timeout" can land in the same
   millisecond. Cancelling the timer is not enough — a callback already running will still fire,
   and the user sees two actions for one press. Each timer gets an `object()` token and the
   callback bails out unless `st["long_token"] is token`.
2. **The `immediate` flag.** Keys without secondary actions fire on press, so release must call
   `up()` rather than firing again — without this flag every key double-fires.
3. **Hold-type singles ignore secondary actions.** `hold` / `holdcombo` / `holdmouse` mean
   "keep it held down", which uses up the press duration needed for long-press detection. Those
   keys take the old path, and the log says so once:
   `<key> 的单击是「按住」型，双击/长按不生效` — it does not fail silently.
4. **`_fire()` strips `repeat`.** See 5.2.
5. **A long press can hold.** If the `long` sub-mapping is itself a hold type, the long press
   only calls `down()` and waits for the release before `up()` — so "long press = hold this key"
   works too.

### 5.4 "Type and send"

```json
"youtube": {"type": "text", "text": "our fixed greeting", "enter": true}
```

`enter: true` appends one Enter (`VK 0x0D` + `SCAN 0x1C`; both are sent so every kind of window
accepts it). In the UI it is the switch under the text box: **"Press Enter after typing (send it)"**.

> Switching the type **to** text auto-checks it; text mappings that already exist keep whatever
> they stored. Uncheck it if you want the text inserted but not submitted.

### 5.5 ⚠️ The upstream UI silently eats these fields (fixed here)

`normalizeConfig()` in `web/index.html` used to keep **only `type / value / mods / text`**:

```js
keys[k] = { type: m.type, value: ..., mods: ..., text: ... };   // ← upstream
```

So `enter`, `repeat`, `double` and `long` were **wiped the first time you pressed Save in the
UI** (the backend was fine; the frontend threw them away first). This fork replaces it with a
recursive `normMapping()`:

```js
if (m.type === 'text' && m.enter) out.enter = true;
if (m.repeat) out.repeat = true;
GESTURES.forEach(function (g) { var s = normMapping(m[g]); if (s) out[g] = s; });
```

> This is the nastiest class of bug: the config file is correct, you open the UI, press Save once,
> and the feature is gone. If a setting ever "doesn't stick" again, look at `normalizeConfig` first.

## 7. The voice key is not HID (important)

The voice key never appears as a HID report. It lives on the ATVV private service:

```
ab5e0001  ATVV voice service
  ├ ab5e0002 [write]   GET_CAPS (0A 00 04 00 01) — puts the remote into recording state
  ├ ab5e0003 [notify]  16 kHz IMA ADPCM, 128-byte frames, no header
  └ ab5e0004 [notify]  b[0]==0x04 pressed / 0x00 released
```

Consequences:

- Key mapping can **never** see the voice key, and `learn` mode cannot capture it.
- **The microphone is owned exclusively by the voice key.** Synthesising Right Alt from another
  key makes the IME show its listening indicator, but the remote sends no audio — the classic
  *"the pill appears but nothing is transcribed"*.

### Related: BLE hands the full service table to the first link only

| How you connect | Services | Contents |
| --- | --- | --- |
| New link `BLEDevice(addr, name, None)` | 5 | 1800 / 1801 / 180a / 180f / 1813 — **no HID, no ATVV** |
| Reusing Windows' existing GATT session `BLEDevice(addr, name, winrt_device)` | **10** | the 5 above + `f000bbc0` / `d343bfc0` / `6c6f6701` / **`ab5e0001`** / `0000feb3` |

So: **let Windows' HID driver hold the link first, then have the voice client join through that
same session.** Reverse the order and you get either keys or voice, never both.

`voice.py`'s `_device_with_details()` does exactly this, but it **silently falls back** to a new
link on failure, which is why it works intermittently. When debugging, look for
`缺少 ATVV 特征（本次枚举到 5 个服务…）` — five services means you got a fresh link.

If it degrades, only pulling the battery for 10 seconds recovers it: the remote firmware wedges
into a "shrunken service table" state after repeated abnormal disconnects. Reconnecting,
restarting the app, or toggling the radio does **not** help. Hence: do not restart the client
repeatedly and do not re-pair repeatedly.

## 8. Startup order and the link guard (the most important fix here)

§7 explains that the HID side must grab the link first — yet upstream starts the roles in the
**opposite** order, so every client restart trips over it again. This section records the full
cause and the fix.

### 8.1 Symptom: the voice key does nothing, then even the D-pad stops working

```
[12:29:29] 客户端已启动
[12:29:29] 语音：连接遥控器 70:4F:10:6D:03:A2 …
[12:29:29] 按键映射：本地 HID 直读（1 个集合，VID_18D1&PID_9450）
[12:29:41] 语音：已连接遥控器 70:4F:10:6D:03:A2
[12:29:41] 语音：缺少 ATVV 特征（本次枚举到 5 个服务：1800, 1801, 180a, 180f, 1813）
[12:29:41] 语音：这台遥控器**没有语音服务**（ATVV，ab5e0001）…      ← wrong conclusion
[12:29:45] 语音：连接遥控器 …（retry every 3 s, forever）
```

Press a D-pad key afterwards and even `[按键] 上 → UP` never appears — **keys and voice die together**.

### 8.2 Root cause: `Roles.start()` starts voice before keys

In upstream `app.py`, `self.voice.start()` runs **before** `self.keytap.start()`. Both threads then
race for the single BLE link:

1. Voice creates a fresh link → per the table in §7 it only sees 5 basic services, no ATVV;
2. Voice reports "this remote has no voice service" and **retries every 3 seconds**;
3. Every failed attempt leaves a **half-open WinRT connection** in the Bluetooth stack, so the
   Windows HID stack can never grab the link again;
4. Keys stop working too — the user sees "the voice key does nothing" while the whole link is
   being killed by our own retries.

Step 2's message is the worst part: it turns a software bug into a hardware verdict.

### 8.3 Fix 1: invert the order and wait for HID to actually hold the link

```python
# app.py  Roles.start()
if self.keytap is None and importlib.util.find_spec("frida") is not None:
    ...
    self.keytap.start()
    _wait_keytap_ready(self.keytap, 3.0)   # ← wait until the HID collection is open
if self.voice is None:
    ...
    self.voice.hid_probe = lambda: bool(getattr(self.keytap, "ready", False))
    self.voice.start()
```

`_wait_keytap_ready()` polls `KeyTap.ready` (set once the local HID handle is open) — tens of
milliseconds in practice, 3 s is only a ceiling. It never blocks startup: if it cannot get a
handle, voice sees "HID is not there" and falls back to connecting on its own.

### 8.4 Fix 2: the link guard — never connect while the remote is asleep

Reordering alone is not enough: voice disconnects and reconnects, and a reconnect can still land
ahead of HID. So `voice.py` gained `_wait_hid_awake()`, evaluated **before every connection
attempt**:

| State | Behaviour |
| --- | --- |
| `hid_probe()` false (HID not holding the link) | No gate; voice connects as before |
| HID holding + a key arrived within the last 20 s | Proceed — that is the only window where connecting works |
| HID holding + remote asleep (outside the window) | **Wait quietly**; no connection, at most one hint per 60 s |

The window is `HID_AWAKE_WINDOW_S = 20.0`. It opens on `poke()`, which the key hook
(`KeyTap.on_activity`) calls for every HID report — **including the voice key itself**.

Two supporting changes:

- Seeing "only 5 basic services" now closes the window immediately (`self._activity_at = 0`),
  handing the link back to HID instead of retrying in a loop;
- The strong "this remote has no voice service" verdict moved from the **first** miss to **three
  consecutive** misses, and the wording is now "most likely" plus a way out (restart, press a key).

### 8.5 Fix 3: re-send GET_CAPS after the remote wakes up

`GET_CAPS (0A 00 04 00 01)` is written only once, right after connecting, while the remote falls
asleep between voice presses. When it wakes it still sends `0x04` ("pressed") but not a single
audio frame — the log shows `本段 0~5 帧`, and it sounds like "the voice key does nothing". Easy to
misdiagnose as a broken key.

`_on_status()` now remembers the frame count of the previous press and, **if that press was starved
(< 20 frames), re-sends GET_CAPS twice on the next press** (immediately and 0.3 s later), which puts
the remote back into recording state.

### 8.6 Fix 4: a three-state HID guard — hands off while the link is rebuilt

After a battery swap or a re-pair, Windows has to rebuild the BLE **HID child devices**, and the
link flaps ("connected → immediately disconnected" in Bluetooth settings) for several rounds. That
is the most fragile moment, and the old code made two mistakes exactly there:

| Mistake | Consequence |
| --- | --- |
| `keys.py` gave up after 2 s and fell back to frida | frida reads **zero reports** on this machine → keys are dead, looking like a hardware failure |
| Voice treated "HID not open yet" as "HID absent" and kept connecting every 3 s | It cut into the rebuild and stretched it indefinitely — that is the flapping |

Fixes:

- **`keys.py` is patient now**: when the HID collection cannot be opened it retries every 2 s (up to
  600 s, with a hint every 30 s); a lost handle retries **forever**. Once local HID reading has ever
  been established it **never falls back to frida** — the worst case here is "wait", not "give up".
- **`app._hid_state()` went from a boolean to three states**:

  | State | Meaning | What voice does |
  | --- | --- | --- |
  | `ok` | local HID reading is running, HID holds the link | connect only inside the 20 s post-press window |
  | `reconnecting` | just acquired (8 s settle) / just lost / still waiting for HID | **never touches the link**, and voids the press window |
  | `absent` | not local HID (frida bypass / device truly gone) | connects on its own; no link-stealing concern |

  `KeyTap.starting` covers "just started, path not chosen yet" and is treated as `reconnecting`;
  otherwise voice misreads it as `absent` and steals the link.

### 8.7 Recovery procedure that actually worked on hardware

If keys **and** voice both stop working, or Bluetooth keeps flapping, follow this order — it is the
sequence that fixed the real machine, not a theoretical one:

1. **Settings → Bluetooth → remove "Chromecast Remote"** (unpair);
2. **Take the batteries out for 10 s**, put them back;
3. **Pair again** (Bluetooth → Add device → hold the remote's pairing combo);
4. Start the client and wait for `按键映射：本地 HID 直读（1 个集合…）`;
5. **Press any remote button** — this lets the HID stack hold the link and opens voice's connect window;
6. Wait for `语音：已连接遥控器` → `语音：链路自检 —— 电量 …` → `语音：就绪`;
7. Hold the voice key and speak.

The "link self-check" line from step 6 is the most useful verdict — if battery/firmware/model read
back, the link is genuinely bidirectional and any later "no sound" is not a link problem:

```
语音：链路自检 —— 电量 95%，固件=26.5，型号=A3，厂商=Google Inc.
```

Reference values from this machine: battery 95%, firmware 26.5, model A3, vendor Google Inc. After
the fix, five consecutive voice sessions produced 93 / 98 / 70 / 140 / 112 frames — at 62.5 frames
per second that is 1.5 s / 1.6 s / 1.1 s / 2.2 s / 1.8 s, and none was a 0–5 frame stub.

### 8.8 How to verify

```bash
python tests/test_gate.py      # 6 guard rules, no remote needed
```

On hardware: restart the client → the log must show `按键映射：本地 HID 直读` **first**, then
`语音：等遥控器醒一次` (not `语音：连接遥控器…`) → press any remote button →
`语音：系统 HID 已握住链路 —— 开始建语音连接` → `语音：已连接遥控器` → **10 services**
(including `ab5e0001`) → `语音：链路自检 —— 电量 …` → `语音：就绪` → hold the voice key →
`语音：▼ 开始` / `▲ 结束（本段 60+ 帧）`.

### 8.9 Fix 5: wait for the **encrypted** link before connecting

This one is the hardest to find, and it is why the same key press sometimes works and
sometimes yields only 5 services.

**Symptom**

```
语音：缺少 ATVV 特征（本次枚举到 5 个服务：
      00001800, 00001801, 0000180a, 0000180f, 00001813）
```

**Diagnostic**: that table does not even contain `00001812` (HID over GATT). A remote that
legitimately holds a HID link cannot enumerate that table — so this is *not* "we stole the HID
link", it is a **fresh link that never completed pairing/encryption**. The remote only exposes
`1812` (HID) and `ab5e` (ATVV) on an encrypted link; unencrypted it hands out only
1800/1801/180a/180f/1813.

**Controlled observation** (same remote, same PC, same day):

| Time | Delay between key press and connect | Enumeration | Result |
| --- | --- | --- | --- |
| 13:16:09 | 15 s (connect timeout + scan) | **10**, incl. `ab5e0001` | 8 voice captures, all good |
| 13:18:42 | almost immediately | 5, no ATVV | failed |
| 13:22:34 | almost immediately | 5, no ATVV | failed |

The difference is **timing**: at the instant of a key press, Windows' HID sub-device is still
negotiating encryption. Whoever connects first decides the encryption state of the link. The old
line "遥控器有按键活动 —— 不再退避，立刻重试连接" was not a feature here, it was the bug.

**Fix**

```python
HID_POST_KEY_SETTLE_S  = 2.5   # after a key press, wait for the handshake before connecting
HID_SETTLE_CAP_S       = 6.0   # but a user mashing the D-pad keeps refreshing the timestamp
UNPAIRED_RETRY_DELAY_S = 8.0   # after grabbing a bad link, do not retry in place
```

The third constant matters as much as the first: grab a bad link → drop it and hand it back →
reconnect "immediately" → grab *another* unencrypted link. That is how three identical bad tables
appeared in a row. Backing off 8 s lets Windows re-establish properly.

**Once this state is written into the Windows GATT cache it does not heal by itself** — fixed code
cannot undo it; the device has to be removed and paired again (see §8.7). After doing exactly that,
13:33:28 produced the full 10-service table:

```
[13:33:28] 语音：服务表 … ab5e0001[ab5e0002:W,ab5e0003:n,ab5e0004:n] …
[13:33:30] 语音：链路自检 —— 电量 95%，固件=26.5，型号=A3，厂商=Google Inc.
[13:33:30] 语音：就绪
[13:33:42] [按键] 语音 → 按住 RALT   ▼ 开始（第 1 次会话）
[13:33:45] ▲ 结束（本段 81 帧音频 ≈ 1.3s）
[13:34:17] [按键] 语音 → 按住 RALT   ▼ 开始（第 2 次会话）
[13:34:19] ▲ 结束（本段 61 帧音频 ≈ 1.0s）
```

### 8.10 Two messages that lied (both fixed)

**① "this remote most likely has no voice service"** — the self-check used to say this after three
consecutive attempts that only saw basic services, steering the user toward "the hardware is
broken". In reality every occurrence of the §8.9 scenario produced exactly that result. It now
branches on whether `1812` is present: `1812` present but no `ab5e` is a genuine "no voice";
no `1812` at all means the pairing/encryption state is gone and the device must be re-paired.

**② "系统 HID 正在重建（遥控器刚换了电池 / 重新配对？）"** — this stayed on screen after every
restart, before any key was pressed. `_hid_state()` conflated "is the link held?" with "have we
seen a key report?": the moment the collections open, `local_hid` is `True`, but `ready` only
flips on the first HID report. It now looks only at `local_hid` plus the `HID_SETTLE_S` (8 s)
settle window. Returning `ok` is safe — `ok` only permits connecting within 20 s of a key press,
so with no key press nothing happens; only the wording changes to "press any remote button".

Measured (collections opened at 13:30:31, UI still claimed "rebuilding" at 13:32:05):

```
[13:30:31] 按键映射：本地 HID 直读（1 个集合…）
[13:31:08] 语音：系统 HID 正在重建（…）        ← false alarm
[13:32:05] 界面：等 HID 稳定（遥控器正在重连）   ← false alarm
```

## 9. Verification checklist

1. Startup log should contain:
   ```
   按键映射：本地 HID 直读（1 个集合，VID_18D1&PID_9450，不经 frida、不需要提权）
   ```
   and it must come **before** any `语音：…` line; the next voice line should be
   `语音：等遥控器醒一次 —— 先按一下遥控器任意键…`, not `语音：连接遥控器…`.
   Seeing "连接遥控器…" means the order regressed — see §8.
2. UI → key mapping status: `运行中（本地 HID 直读）`.
3. Press a D-pad key → `[按键] 上 → UP（按住·连发）`; **holding must keep moving**.
   The first press should also produce `语音：系统 HID 已握住链路 —— 开始建语音连接` and
   `语音：已连接遥控器`.
4. After connecting there should be `语音：链路自检 —— 电量 xx%，固件=…，型号=…，厂商=…`.
   **If it reads back, the link is bidirectional**; only a failed read points at the link (then run
   the recovery procedure in §8.7).
5. Hold the voice key → `语音：▼ 开始`, release → `语音：▲ 结束（本段 N 帧音频 ≈ x.xs）`.
   Frames must be well above zero (≈62.5 frames per second of speech — a 1.5 s sentence is ~93);
   a handful of frames means the remote never entered recording state — GET_CAPS is re-sent on the
   next press (§8.5).
6. **Double click**: map "double → `Esc`" on a key, press it twice quickly — only `Esc` fires,
   **never** the single action as well. A single press fires the single action after 0.3 s
   (expected, see §5.2).
7. **Long press**: map "long → open URL", hold for 0.6 s and release — only the URL opens,
   the single action does not fire.
8. **Send**: map a `text` with "Press Enter after typing" checked, press the key with an input
   box focused — the text should be **submitted immediately**, no second OK press.

If step 1 instead shows `按键映射：暂时没打开遥控器的 HID 集合 —— 每 2 秒重试`, the remote is not
connected yet (or Windows has not loaded the HID child devices): **press any remote button** and the
client picks it up within 2 s; voice will report `系统 HID 正在重建` and stay off the link meanwhile
(§8.6).

If it shows `挂上蓝牙驱动宿主 WUDFHost (PID …)`, it waited the full 10 minutes and fell back to frida
(**it never falls back once local reading has been established**). frida reads nothing on this machine
— re-pair per §8.7.
